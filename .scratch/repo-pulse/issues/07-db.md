# 06 — Storage (`db`)

**What to build:** A SQLite repository that bootstraps the schema (per spec) and exposes typed write methods. No analytics queries — those live in the Analytics ticket. The Collector and Analytics layers both depend on this.

**Blocked by:** 02 — Config

**Status:** ready-for-agent

- [ ] `Database` class taking a `Path` to the SQLite file
- [ ] `bootstrap()` creates the schema idempotently (matches spec: 4 tables `repositories`/`snapshots`/`topics`/`repository_topics`, 3 indexes)
- [ ] `upsert_repository(repo: dict, today: date) -> None` handles insert + update; sets `first_seen_date` only on first insert, `last_seen_date` on every call; sets `in_watchlist` from a separate `in_watchlist: bool` parameter
- [ ] `write_snapshot(full_name: str, snapshot_date: date, fields: dict) -> None` is UPSERT on `(full_name, snapshot_date)`
- [ ] `upsert_topics(full_name: str, topic_names: list[str]) -> None` creates new topics and links them
- [ ] `get_repository(full_name: str) -> dict | None`
- [ ] `get_previous_snapshot(full_name: str, before_date: date) -> dict | None` returns the most recent prior snapshot
- [ ] `list_watchlist() -> list[str]` returns all `full_name` with `in_watchlist = 1`
- [ ] All methods use context manager for connection; transactions on writes
- [ ] Tests use in-memory SQLite (`:memory:`) via `Database(":memory:")`
- [ ] Tests cover: bootstrap idempotency, upsert insert vs update, snapshot UPSERT (re-run same day), topic upsert (new + existing), get_previous_snapshot ordering
- [ ] All 22 snapshot fields per spec are written (not just the original 8)
