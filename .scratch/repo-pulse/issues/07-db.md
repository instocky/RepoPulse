# 06 — Storage (`db`)

**What to build:** A SQLite repository that bootstraps the schema (per spec) and exposes typed write methods. No analytics queries — those live in the Analytics ticket. The Collector and Analytics layers both depend on this.

**Blocked by:** 02 — Config

**Status:** ready-for-agent

**Sync notes (vs. `docs/SPEC.md`):**
- The original ticket wording said "`first_seen_date` only on first insert". The spec is the authority: §Watchlist lifecycle explicitly says "Re-starring (manually by the user) is a fresh entry: `in_watchlist = 1` again, `first_seen_date` reset." The implementation now resets `first_seen_date` on the `in_watchlist` 0→1 transition, not just on the first insert. The original ticket wording was the mistake; this ticket is now in sync with the spec.
- The original ticket said "All methods use context manager for connection". The implementation owns a single connection per `Database` instance instead — see the connection-lifecycle bullet below for why. The deviation is forced by SQLite's per-connection `:memory:` semantics, which the test suite relies on.

- [ ] `Database` class taking a `Path` to the SQLite file (or the literal string `":memory:"` for tests; SQLite's per-connection memory-store convention)
- [ ] `bootstrap()` creates the schema idempotently (matches spec: 4 tables `repositories`/`snapshots`/`topics`/`repository_topics`, 3 indexes)
- [ ] `upsert_repository(repo: dict, today: date) -> None` handles insert + update; sets `first_seen_date` on first insert and on `in_watchlist` 0→1 transition (re-star), preserves it on continuous membership, on unstar, and on 0→0 re-upsert; sets `last_seen_date` on every call; sets `in_watchlist` from a separate `in_watchlist: bool` parameter. The reset is implemented atomically inside the UPSERT statement (a `CASE` on the existing `in_watchlist`) — see `docs/SPEC.md §Watchlist lifecycle` for the rationale.
- [ ] `write_snapshot(full_name: str, snapshot_date: date, fields: dict) -> None` is UPSERT on `(full_name, snapshot_date)`
- [ ] `upsert_topics(full_name: str, topic_names: list[str]) -> None` creates new topics and links them; deduplicates names within a single call
- [ ] `get_repository(full_name: str) -> dict | None`
- [ ] `get_previous_snapshot(full_name: str, before_date: date) -> dict | None` returns the most recent prior snapshot (strict `<` on `snapshot_date`)
- [ ] `list_watchlist() -> list[str]` returns all `full_name` with `in_watchlist = 1`; order is not part of the contract (the Analytics layer sorts if it needs determinism)
- [ ] **Connection lifecycle**: the `Database` owns a single `sqlite3.Connection` for its lifetime. The `Database` is itself a context manager — `with Database(path) as db: ...` opens the connection in `__init__` and closes it on `__exit__`, including on exception. The Collector relies on this so a mid-run traceback does not leave the SQLite file locked. Per-method connection is NOT used: SQLite's `:memory:` is a per-connection private store, so opening a new connection per method would return a different (empty) database on each call and break the in-memory test fixture.
- [ ] **Write transactions**: every write method (`upsert_repository`, `write_snapshot`, `upsert_topics`) is wrapped in a per-call transaction. Commits on normal exit, rolls back on any exception (`BaseException` so `KeyboardInterrupt` does not leave a partial write). The Collector and Dashboard are separate processes sharing the SQLite file, so a partial write would surface as a dangling row in the next Collector run.
- [ ] Tests use in-memory SQLite (`:memory:"`) via `Database(":memory:")`
- [ ] Tests cover: bootstrap idempotency, upsert insert vs update, snapshot UPSERT (re-run same day), topic upsert (new + existing + duplicates within a single call), get_previous_snapshot ordering, re-star transition (0→1 resets `first_seen_date`), 0→0 upsert (preserves `first_seen_date`), close idempotency, context-manager release on exception
- [ ] All 22 snapshot fields per spec are written (not just the original 8)
